AI飲み会アプリ「hinayoi（ひなよい）」

# 概要

自分と、複数のAIキャラ（女の子）が参加する飲み会で楽しく会話する

# 環境

サーバ：AWS EC2(このサーバ), RDS(MySQL), ALB
  DBの接続情報は、/var/www/kpi/config/database.phpから取得してください。データベースは"hinayoi"を新規作成
開発言語：Next.js（本サーバでのポートは7500を使用する）
ブラウザー：Google Chrome(Desktop)
音声再生：ElevenLabs TTS

# 会話方法

## AIキャラの会話生成

AIキャラは４人参加
各キャラが、Gemini 3.5 Flash（最近リリースされた。モデル名："gemini-3.5-flash"）を使い、下記を含むプロンプトより、次の会話を生成する

- 性格設定プロンプト（４人それぞれ）
- 現在の話題（後述）
- 会話履歴（過去30件分。話者＋内容）
- 会話指示（会話の目的、ルール、禁止事項等）これは全キャラ共通

## キャラ毎の会話ポイントについて

- 会話ポイントは、キャラ毎に設定される

会話ポイントテーブルのイメージ
+------+--------+
|名前  |ポイント|
+------+--------+
|ひな  |      10|
+------+--------+
|こはる|      25|
+------+--------+
|みさき|     130|
+------+--------+
|ひより|      85|
+------+--------+

- 会話ポイントは飲み会セッション毎に独立（nomikai_session_character_points テーブル）
- 会話ポイントの初期値は0-100のランダム（セッション作成時に各キャラへ乱数 seed）
- 会話ポイントが100を越えたキャラ（複数人いる場合はランダム抽選）が次の話者になる
　100を越えたキャラがいない場合は、一番会話ポイントが大きい人が次の話者になる
- 会話ポイントは、全員、10秒で10ずつ増える（自動）
- 各キャラおよびユーザーの会話で、テキストに、名前が「含まれている」場合は、
　そのキャラの会話ポイントを+100する。
　この判定は会話生成/入力直後に行う
　「含まれている」判定は、文字列の一致で行う
　例：...について、ひなさんはどう思いますか？　→　ひなのポイント+100
　名前でない部分のテキストで偶然による一致を許容する
- 会話を生成したら、会話ポイント-100（ミニマムは0）


## 会話生成手順

1.話者の決定
　会話ポイントが100を越えたキャラ（複数人いる場合はランダム抽選）が話者になる
　100を越えたキャラがいない場合は、一番会話ポイントが大きい人が話者になる
2.会話テキストの生成
　Gemini 3.5 Flashを呼び出して、会話テキストを生成し、履歴DBに保存する
  会話ポイントの再計算（会話に名前が出た人+100, 話者の会話ポイント-100）
3.ElevenLabs TTSを呼び出して、音声データを取得する
4.会話テキストを画面表示開始すると同時に、音声再生を開始する
　※会話テキストはタイプライター風に１文字ずつ表示する。早さは7文字/s。
　　音声とテキストの表示速度は一致しないが、経験上この早さで体験上の違和感は最小限になる
5.1に戻る

## ユーザーの音声入力

手入力および、Chromeの、Web Speech APIを使った音声入力でテキストを入力できる
入力したテキストは画面に表示すると共に、会話履歴DBに保存される
これは、キャラの会話生成と並列で行われる
テキストに名前が出た人の会話ポイント+100

## 現在の話題について

話題マスターテーブルをDBに作っておきます
ここには、話題のテキストを何件か登録しておきます。

開始時点で、ランダムに話題が選択され、画面に表示されます。

その後、4分おきに、ランダムに話題が選択されなおして、画面が更新されます。
ただし、通常話題が3回連続したら、間に「追加注文タイム」（30秒）を挟む。

会話生成プロンプトに含めるのは、現在選択されている話題になります

## 読み間違い、認識間違い対策

ElevenLabsがよく読み間違えるテキストは、ひらがなに直す対応リストを作っておき、TTS APIに渡すテキストはこのリストに沿って置き換えたものにする。画面表示テキストは置き換え前のものでよい
例：頑張ろう→がんばろう
この置き換えリストは増えていく可能性大


ユーザーの音声認識について、名前を読んだときに漢字にされる場合が多いのでこちらも置き換えリストを作る
陽菜→ひな
小春→こはる
※置き換え後に、ＤＢに保存したり、会話ポイント判定を行う。

# ログイン機能

ログインＩＤ，パスワード，ニックネームを `users` テーブルに保管。
新規ユーザー登録UIは無く、CLI（`scripts/add-user.mjs`）で手動追加する。

```
node --env-file=.env.local scripts/add-user.mjs <loginId> <password> <nickname>
```

- ニックネームはユーザーの発言時の speaker_name として保存され、UIにも表示される
- prompts/*.md 内の `{nickname}` プレースホルダはプロンプト組み立て時に置換される

# 飲み会セッション

「１回の飲み会」を表すセッションを `hinayoi_nomikai` cookie（ブラウザセッションクッキー、UUID）で管理する。

- ブラウザ起動毎に新ID発行 → 過去の会話履歴とは独立した新規セッションになる
- ページリロードでは継続
- `conversations` 行は `nomikai_session_id` で紐付き、プロンプトの履歴取得もセッション単位
- 話題ローテーション状態（`nomikai_sessions`）と会話ポイント（`nomikai_session_character_points`）もセッション単位
- 複数ユーザー同時利用でも互いに干渉しない

# 追加注文タイム

通常話題が3回続いた節目に、話題切替フックとして「追加注文タイム」を1回挟む。

- 通常話題: 4分 × 3回
- 追加注文タイム: 30秒（テキスト「追加注文タイム」を画面表示）
- プロンプトで最優先指示として「飲み物/食べ物を注文するセリフのみ」と指示
- 追加注文タイム終了後、最優先指示として「新しい話題に戻って会話再開」を伝える

# 飲み会終了（ラストオーダー → 締めの挨拶 → 終了画面）

飲み会の最大時間（α版は1時間固定）を超えたら自然な流れで幕引きする。

- セッション開始時刻は `nomikai_sessions.created_at` を使い、終了予定時刻は `created_at + 1時間`
- 話題ローテーション種別 `current_topic_kind` に `closing` / `ended` を追加
- 進行フロー
  1. 残り5分以下になると、話題バーの左隣に小さな赤バッジ「残り5分▼」をパルス表示（予告）
  2. 終了予定時刻を超えた後、次の話題ローテーションのタイミングで `closing`（締めの挨拶タイム、2分）に遷移し、話題テキストを「飲み会終了」に切替
  3. `closing` 中はプロンプト最優先で「楽しかった気持ち・感謝・別れの挨拶」を指示。ユーザー側からの発言も可
  4. 2分経過で `ended` に遷移。クライアントは画面全体に半透明グレーのオーバーレイ＋中央に「この飲み会は終了しました」を表示
  5. `ended` 中はターンループ・音声認識・テキスト入力・送信ボタンを全て無効化。発話中だった音声は即停止し、キャラ画像も `_default` に戻る
- 終了予定時刻を過ぎても、現在の話題が自然に切れるまで待ってから遷移するため、実際の終了は最大「1時間 + 1話題分」になる
- 「残り5分▼」表示は `closing` / `ended` 状態では非表示
- API 側のガード
  - `POST /api/turn/next`: `ended` なら発話生成せず `spoke: null` を返す
  - `POST /api/conversations`: `ended` なら 403 でユーザー入力を拒否
